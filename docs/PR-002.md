# PR-002: 修复导出功能（服务端全量导出）+ 补充跟踪模块导入模板 + 修复服务部署

## 变更说明

1. **导出功能彻底修复**：从"前端传当前页数据"改为"服务端查询数据库全量导出"
2. **补充 tracking 模块批量导入模板**
3. **修复服务无法启动/访问问题**

## 问题与修复

### 问题1：所有导出功能无法实现

**根因**：原来导出是**前端驱动**的——前端把当前页显示的 20 条数据 (`tableData`) 传给后端，后端只是把数组转成 CSV。导致：
- 只能导出当前页的 20 条，无法导出全量数据
- 严重依赖前端数据加载状态

**修复**：重写 `POST /api/export` 为服务端导出：
- 新增 `EXPORT_MODEL_MAP`：22 个 API 路径到 SQLAlchemy 模型的映射
- 前端传 `{"source_api": "/api/warehouse/receipts", "params": {...}, "format": "csv"}`
- 后端根据 `source_api` 定位模型 → 应用过滤条件 → 查询全量数据 → 输出 CSV
- 自动排除内部字段（`id`, `is_deleted`, `password_hash` 等）
- 保留旧版 `{"data": [...]}` 格式向下兼容

### 问题2：tracking 模块缺少导入模板

**根因**：tracking 页面有列表展示，但缺少 `import/template` 端点，与其他 20 个模块不一致。

**修复**：新增端点：
- `GET /api/tracking/list/import/template` — 下载 Excel 模板
- `POST /api/tracking/list/import` — 批量导入（含校验：环节可选值、跟踪编号唯一性）

### 问题3：项目无法启动/访问

**根因**：
- `run.py` 默认端口 5000，但 nginx 配置代理到端口 8002
- 无 systemd 服务，重启后不自动启动
- `debug=True` 写死，systemd 下 reloader 子进程可能导致管理异常

**修复**：
- 创建 `/etc/systemd/system/cross-border-logistics.service`，监听 `127.0.0.1:8002`
- `run.py` 改为 `FLASK_DEBUG=1` 环境变量控制 debug 模式
- `systemctl enable --now cross-border-logistics` 设置开机自启
